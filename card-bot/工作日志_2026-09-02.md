## 修复：平铺型分享（顶层条目 > 32）转存不完整导致永久卡死

### 现象
链接 https://115cdn.com/s/sws4b3g3w1n?password=1111（凡人修仙传 256 集，510GB）
每次都卡在比对循环，日志刷屏「目标目录尚未达到源分享基准」，最终失败。
网盘里留下一堆残骸目录，每个内层目录**恰好 32 个子项 / 40.42 GB**。

### 根因（用户直觉正确：就是「没有主文件夹」导致的）
1. **115 的 `share_snap` 接口默认每页只返回 32 条**（实测：不传 limit → 32 条，
   limit=100 → 100 条，limit=1000 → 256 条，offset 分页正常）。
2. **P115-Share 从不传 limit/offset，也从不翻页** → 顶层条目 > 32 的分享
   （没有单一主文件夹、文件平铺在根目录）**只会被转存前 32 个**。
3. cardbot 用 `fetch_share_video_files` 递归拿到的是**完整 256 个名字**，
   而 P115-Share 只转了 32 个 → `top_match = 32 == 256` 恒为 False。
4. 比对循环的两个完成分支**都要求 top_match**，连「体积停滞」兜底分支也被堵死
   → 空转到 45 次轮询上限 → 卡死。
5. 附带 bug：`original_file_count` 从 `share_info` 取 count，但 count 在 `data` 层，
   `shareinfo` 里没有 → 恒为 0（已确认，本次未改，因翻页修复后不再依赖它）。

### 修复（已应用并验证）
- **A**：`_share_snap_with_fallback` 注入 `limit=1000 / offset=0 / cid=0`，
  并新增 `_paginate_share_snap()` 按 `data.count` 自动翻页取全。
- **B**：比对循环新增二级兜底 —— 体积连续 12 轮停滞且 `current_total>0`
  即按当前内容判定完成，不再死等 top_match。

### 验证结果
- `_share_snap_with_fallback` 返回：32 条 → **256 条** ✅
- 端到端 `_save_share_link_internal`：`检测到 256 个项目`（原为 32）✅

## 2026-09-03 凌晨：修复 TG bot「发送没反应」——entrypoint 被镜像覆盖

### 现象
用户在 TG 发链接给机器人完全没反应，日志里也无任何消息处理记录。

### 根因（关键踩坑）
容器主进程是 `python -m app.main`（P115-Share API），不是 cardbot！
- 22:15 我用 `docker run ... listeningltg/p115-share:latest python /cardbot/cardbot.py`
  重建容器时，**没加 `--entrypoint`**。
- 该镜像自带 entrypoint `./entrypoint.sh`，它 `exec python -m app.main`，
  **把 Cmd 参数整个忽略** → cardbot 根本没跑，TG polling 不存在 → 消息石沉大海。
- 验证方法：`docker exec p115-card-bot cat /proc/1/cmdline` 看到 `python -m app.main` 即实锤。

### 修复（正确姿势）
```bash
docker run -d --name p115-card-bot --restart unless-stopped \
  -v /vol2/1000/docker/115/card-bot:/cardbot:ro \
  -v /vol2/1000/docker/115/card-bot/state:/cardbot-state \
  -v /tmp/p115share_cookies:/tmp/p115share_cookies \
  -e TZ=Asia/Shanghai \
  --entrypoint python listeningltg/p115-share:latest /cardbot/cardbot.py
```
要点：**`--entrypoint python` 必须显式指定**，镜像 entrypoint 才不会被继承。

### 验证
- `/proc/1/cmdline` = `python /cardbot/cardbot.py` ✅
- 发链接 swsy13l3w7v（指环王3 {tmdbid=122}，158.21GB 单文件夹）立即响应：
  识别 ✅ → 转存 ✅（169876693975 ≈ 基准 169878698275，3 次稳固）→ 创建分享 ✅
- 指环王3 在等 115 审核轮询（状态=0），属正常流程，重试队列接管。

### 教训
1. 该镜像 entrypoint 会吞掉 Cmd——**凡手动 docker run 必带 `--entrypoint python`**。
2. 排查「bot 没反应」第一步永远是 `/proc/1/cmdline` 确认主进程是谁。
3. docker-compose.yml 里的 `entrypoint: ["python", "/cardbot/cardbot.py"]` 是数组形式
   直接覆盖镜像 entrypoint，所以 compose 启动一直正常；手动 run 不带该参数就会踩坑。
